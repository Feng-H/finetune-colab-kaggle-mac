3.0 硬件地基：GPU 到底是什么（零基础版）

在碰真卡之前，把三个 hardware 问题讲透。不假设任何计算机体系知识。

CPU vs GPU：教授军团 vs 小学生军团

你的电脑里有两个「算东西的芯片」：

  • CPU：少量超强核心（几个到十几个），每个都能处理复杂逻辑——适合「一步一步、每步都不一样」的任务。你平时跑 TS 代码、开浏览器都是它。
  • GPU（显卡）：几千个简单核心（T4 有 2560 个），每个只会算加减乘，但全员同时上阵——适合「海量一模一样的简单计算」。

类比：CPU = 几位数学教授，GPU = 三千个会算术的小学生。算一亿道乘法题，教授输惨（他再快也只有几个人）；写一篇论文，小学生不行。而 LLM 的核心运算（矩阵乘，1.0 节的 @）恰好就是「一亿道独立的小乘加」——GPU 的完美猎物。这就是为什么训练模型全在 GPU 上。（「教授 vs 小学生军团」是行业通用讲法，属翻译层；对回乐队：三千名和声团员同时开嗓，一人一句简单和声。）

内存 vs 显存：两个独立的仓库

CPU 和 GPU 各自用各自的仓库：内存（RAM）给 CPU 用（几十 GB）；显存（VRAM）给 GPU 专用（T4 只有 16 GB）。关键规则：GPU 只能直接算显存里的数据——所以 device="cuda" 的意思是「把这块张量从内存搬到显存」（搬运本身耗时，以后会遇到「搬比算还慢」的场景）。你第 2 章记的账本，记的就是显存这个仓库的容量。

术语身份证（首次出现，从零解释）

核心 core        GPU 里干活的计算单元（T4 = 2560 个）
CUDA             NVIDIA 的 GPU 编程软件层；device="cuda" 的 cuda 就是它
kernel 核函数     发给 GPU 千核并行执行的一段计算程序（算子的硬件形态）
FLOPS            每秒浮点运算次数 = 显卡的马力；T4 ≈ 65 TFLOPS（fp16）
nvidia-smi       显卡的「任务管理器」命令，看占用/卡型

T4 是谁：NVIDIA 2018 年的卡，2560 核 + 16GB 显存，Colab/Kaggle 免费档的主力。它的 65 TFLOPS 意味着：理论上每秒 65 万亿次浮点运算——你 3-B 那一亿参数的实验在它面前是眨眼间的事。

3.2 测量三件套

▶ 上机约定

带 ▶ 的代码块 = 在 T4 会话里新建单元格、意接粘贴运行。今日顺序：▶例 3-1（交 3-A）→ ▶例 3-2 补全（交 3-B）→ 练习 3-C 的循环（先预测再跑）。

所有验证围绕三个 API（外加一个重置）：

▶ 例 3-1 · 第一个要跑的格子：基线 + 一次分配的手算对照

import torch

torch.cuda.init()
print(torch.cuda.get_device_name(0))          # 确认卡型：Tesla T4
print(f"基线 allocated: {torch.cuda.memory_allocated()/2**30:.2f} GB")   # ≈0

a = torch.zeros(10**8, device="cuda")          # 1 亿个 fp32
print(f"分配后 allocated: {torch.cuda.memory_allocated()/2**30:.2f} GB") # ？？
del a; torch.cuda.empty_cache()

手算：10⁸ 参数 × 4 字节 = 0.4×10⁹ 字节 = 0.37 GB（10⁹ 字节按二进制 GiB 折算 ≈ 0.373GiB；换算尺给的是十进制 GB，读数差 7% 属正常）。memory_allocated 是 torch 视角的在用显存；max_memory_allocated 是历史峰值；reset_peak_memory_stats() 归零峰值刻度。

读者问答

问：为什么 nvidia-smi 显示的占用比 memory_allocated 大？

答：torch 有缓存分配器（caching allocator）：你 del 掉的张量，显存不立刻还给显卡，而是留在 torch 自己的池子里下次复用（省去反复向驱动申请的开销）。所以 nvidia-smi 看到「已预留」（reserved，含池子），memory_allocated 只算「在用」。排 OOM 时两个数都要看：allocated 高=真用得多；reserved 高而 allocated 低=池子碎片，empty_cache() 可释放（但它不是万能药，别在训练循环里频繁调用）。

3.3 验证「训练态 = 权重 × 4」

你在 2-A 推导过 16 字节/参数，现在用一亿个假参数在真卡上验它。关键背景：显存不是训练一开始就占满，而是分时刻出现——权重在创建时、梯度在 backward 时、动量（优化器状态）在首次 step 时——所以在三个时刻各读一次表。下面是完整注解版，直接复制运行（设计原则：例题必完整、逐行有来历；挑战只在练习里）：

▶ 例 3-2 · 完整注解：三段增量测训练态

import torch

p = torch.zeros(10**8, device="cuda", requires_grad=True)   # 一亿个假参数=权重
opt = torch.optim.AdamW([p], lr=1e-3)      # 优化器：管 [p]，步长 lr；此刻未占显存

base = torch.cuda.memory_allocated() / 2**30
print("① 权重（创建时）:", round(base, 2), "GB")            # 预期 ≈0.37

loss = p.sum()        # ①前向+②损失：一亿个数加成标量（最简 loss）
loss.backward()       # ③反向：给每个参数算梯度（例 1-1 的同一调用）
print("② 梯度（backward 时）:", round(torch.cuda.memory_allocated()/2**30, 2), "GB")

opt.step()            # ④更新：首次真正动参数，顺手创建两份动量
print("③ 动量（首次 step 时）:", round(torch.cuda.memory_allocated()/2**30, 2), "GB")

预期：0.37（权重）→ 0.75（+梯度 0.37）→ 1.49（+动量 0.75）≈ 0.37×4——第 2 章公式在真卡上兑现。

读者问答（教学事故 #3 存档）

练习 3-B · 训练态×4 实测（A 级：跑通 + 改一个数）

  1. 复制 ▶例 3-2 完整版到 T4 会话，跑通，抄下三段读数。
  2. 把 10**8 改成 10**7，先用换算尺预测三段读数各变多少，再跑验证。
答案（学生实测 · 已批改，含翻车实录）

第一轮（10⁸）：0.37 → 0.75 → 1.49，与 16 字节/参数法则精确一致，2-A 推导在真卡兑现。

第二轮（改 10⁷ 未清场）：实测 0.78 / 0.07 / 0.15。破案：① = 旧权重 0.37 + 旧梯度 0.37（被旧 loss 的计算图拽着未释放）+ 新权重 0.04；② = loss = p.sum() 重绑定时旧图整体释放（-0.74）+ 新梯度（+0.04）的净额；③ 正常。三条教训：notebook 会话有记忆（改数重跑≠干净重跑）；计算图拽着显存（loss 多活一秒参数多占一秒）；数字对≠理解对（② 是两股大变动抵消的巧合）。清场代码（放进实验 cell 开头，实验之间也要清，不是只在新会话清一次——学生同型二犯实录）：for name in ["p","opt","loss"]: globals().pop(name, None) + gc.collect(); torch.cuda.empty_cache()。

最终收官（10⁷ 干净复测）：0.04 / 0.07 / 0.15 ✓ 与换算尺预测一致，3-B 关闭。

练习 3-C · OOM 演练（先预测再动手）

  1. 先手算：T4 16GB，循环里每次 torch.zeros(10**9, device="cuda")（fp32）并 append 进列表，第几次迭代会爆？
  2. 写下预测后跑：
    x = []
for i in range(100):
    x.append(torch.zeros(10**9, device="cuda"))
    print(i, f"{torch.cuda.memory_allocated()/2**30:.2f} GB")
  3. 读报错：CUDA out of memory 那行里 "Tried to allocate ..." 告诉你什么？和你的预测差几次迭代？为什么（提示：显存里还有谁）？
  4. 修复：改成「用完即弃」（不 append，每轮覆盖同一变量），再跑通 100 轮。
答案（已批改 · 含前传实录）

循环题答案：每块 3.73 GiB、可用约 14.4 GiB → 第 4 次分配（i=3）爆，列表已躺 3 块=11.19 GiB；遗言 "Tried to allocate 3.73 GiB" 即第 4 块。粗糙预测 16÷3.7≈4.3 会误判能塞 4 块——卡实际可用 14.56 GiB（十进制 16GB=14.9 GiB 再扣驱动）。修复：append 改每轮覆盖 x = torch.zeros(...)（旧引用被替换即释放，进缓存池复用）→ 100 轮畅通。

意外前传（2026-09-26）：学生把例 3-2 改成 10⁹ 参数版，训练态×4 实验自己爆在 opt.step()——爆点=动量到账时刻，验证 3.0 时机直觉。遗言解读：Tried to allocate 3.73 GiB＝第二份动量；in-use 11.18＝3.73×3 精确对账；「16GB 卡」实际可用 14.56 GiB（十进制 16 GB＝14.9 GiB 再扣驱动）——单位差在生死线咬人：需求 14.9 vs 可用 14.56。预判教训：10⁹ 全参训练态＝14.9 GiB > 可用，跑之前就该判死刑——账本的意义即免点火而知炸。

算子 operator（op）
对张量的一次计算（@、sum、backward…），背后是 GPU 核函数；与「造张量」（分配内存如 torch.zeros）相对，是计算图的节点
caching allocator
torch 的显存池：释放的张量留在池内复用，reserved ≥ allocated
reserved / allocated
nvidia-smi 口径（含池）/ torch 口径（在用）的两种显存读数
peak memory
max_memory_allocated 记录的历史峰值——比终值更能暴露瞬时爆点
CUDA OOM
显存耗尽的运行时错误；报错含申请大小与当前占用，是排障第一线索
