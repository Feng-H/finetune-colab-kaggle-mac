第 9 章 · 超参三剑客：学习率、有效批次与自动化评估

在第 9 章中，我们亲眼见证了 Step 40 泛化巅峰与后期的死记硬背反弹。本章彻底告别「盲目碰运气」：学会用早停机制（Early Stopping）在谷底自动踩死刹车；拆解控制训练节奏的「超参三剑客」（学习率、有效批次、退火调度器）；最后跳出单一 Loss 视角，建立工业级的大模型裁判评测体系。

本章你将学会

  • 自动捕获最优模型：掌握 EarlyStoppingCallback 与 load_best_model_at_end，让训练在验证集拐头时自动刹车并回滚到最佳权重
  • 超参三剑客原理：
    • 学习率（Learning Rate）：为什么它是大模型的第一旋钮？过大炸炉、过小爬行
    • 有效批次大小（Effective Batch Size）：显存受限时，如何用梯度累加（Gradient Accumulation）以时间换空间
    • 退火调度器（LR Scheduler）：为什么不能一个速度跑到底？解析 Warmup 热身与 Cosine 余弦衰减
  • 跨越 Loss 盲区：理解为什么「Loss 最低」不等于「业务表现最好」，掌握自动化评测与 LLM-as-a-Judge（大模型裁判） 的工业级评测范式

8.1 接续悬念：在巅峰自动刹车的「早停机制」

回顾你在第 9 章练习 6-B 中跑出的这组震撼数据：

  • 第 20 步：Val Loss = 2.235
  • 第 40 步：Val Loss = 2.183（★ 全场最低，泛化最强）
  • 第 60 步：Val Loss = 2.205（开始回升）
  • 第 80 步：Val Loss = 2.229
  • 第 90 步：Val Loss = 2.234（彻底回到起点）

在第 9 章，程序傻傻地一直跑到了第 90 步结束，最终保存在磁盘里的也是第 90 步那个「死记硬背」的坏模型。在真正的工业训练中，一次训练可能要跑几天几夜，我们不可能搬着板凳通宵盯着屏幕手动按停止键。

解决方案：Early Stopping（早停机制）+ 自动加载最佳权重。

▶ 例 8-1 · 配置自动早停机制（EarlyStoppingCallback）

from transformers import TrainingArguments, EarlyStoppingCallback
from trl import SFTTrainer

# 1. 配置训练参数：必须启用 save_strategy 并与 eval_strategy 对齐
training_args = TrainingArguments(
    output_dir = "outputs_early_stopped",
    per_device_train_batch_size = 8,
    per_device_eval_batch_size  = 8,
    num_train_epochs = 5,              # 可以放心地把总轮数设大
    learning_rate = 2e-4,
    eval_strategy = "steps",           # 按步数评估
    eval_steps = 20,                   # 每 20 步考一次试
    save_strategy = "steps",           # 必须与 eval_strategy 一致
    save_steps = 20,                   # 每次考试的同时保存一份 Checkpoint
    save_total_limit = 2,              # 硬盘有限，只留最好的 2 份
    load_best_model_at_end = True,     # ★ 核心：训练结束后自动回滚到考分最高的那个 Checkpoint！
    metric_for_best_model = "eval_loss",# 以验证集 Loss 最小作为评判标准
    greater_is_better = False,         # Loss 越小越好
    logging_steps = 10,
    report_to = "none"
)

# 2. 注入早停回调守卫：设置耐心值 (patience)
trainer = SFTTrainer(
    model = model,
    tokenizer = tokenizer,
    train_dataset = train_ds,
    eval_dataset = eval_ds,
    dataset_text_field = "text",
    max_seq_length = 2048,
    args = training_args,
    callbacks = [
        # 耐心值设为 2：如果连续 2 次考试（40 步）成绩都没有刷新历史纪录，直接掐断训练！
        EarlyStoppingCallback(early_stopping_patience = 2)
    ]
)

核心工作机制：耐心值（Patience）

如果第 40 步考出了历史最低 2.183，记录被锁定。到了第 60 步考了 2.205（没有进步，耐心值剩 1）；到了第 80 步考了 2.229（依然没有进步，耐心值耗尽清零！）。

Trainer 会当场主动踩死刹车，终止后续无意义的轮次，并凭借 load_best_model_at_end=True，自动将内存里的模型指针还原到第 40 步时的巅峰状态！

读者硬核发问：如果是 Step 35 最佳呢？要不要二阶段放大镜重跑？

问：“我们在 Step 40 抓到了最低点，但这是因为我们设了 eval_steps=20（每隔 20 步测一次）。真实的最优解完全有可能落在 Step 35！我们能不能先粗测找出 40，再在 20~60 之间拿放大镜（比如每 2 步测一次）再跑一遍来抓出绝对真神？”

答：完全可以，而且你在直觉中推导出了打比赛和学术界常用的「二阶段网格细化搜索」！但在真实工业界，工程师通常不会过度追求抓出那个精确的 Step 35，原因有三：

  • 1. 损失平原效应（Flat Minima / 盆地假说）：
    大模型参数空间的最优点不是一个针尖，而是一个相对平缓的宽阔盆地。从 Step 35 到 Step 40，虽然权重变了 5 次，但考卷 Loss 差异通常只有极其微弱的 0.003（比如 2.180 vs 2.183），在人类的实际文本生成体验上，根本感知不到任何区别。
  • 2. 评估本身有昂贵的时间开销（Evaluation Overhead）：
    每次算 Validation Loss，GPU 都必须暂停训练、把整个考卷全量前向推理一遍。如果每隔 2 步甚至每步都跑一次评估，GPU 大部分时间都在“做考卷”而不是“学习”，整体训练耗时会暴涨 3~5 倍！
  • 3. 验证集本身的微小随机噪声：
    验证集只有几十或几百条。Step 35 偶尔比 Step 40 低了 0.002，很可能只是验证集里的某一句话碰巧猜中了概率，并不代表整体泛化能力具有统计学显著优势。
  • 工业黄金法则：根据算力预算把 eval_steps 设为总步数的 5%~10%（比如 100 步的微调设 eval_steps=10，几千步的训练设 eval_steps=100），抓到盆地区间即收工。只有在打 Kaggle 比赛争夺小数点后第四位、或发顶会论文时，才会从 checkpoint-20 resume 出来拿放大镜做精细化二阶段搜寻。

8.2 掌控训练节奏：超参三剑客

很多新手调参靠猜，被戏称为「玄学炼丹」。其实，大模型训练动力学中最核心的三个旋钮有着极其清晰的因果逻辑：

旋钮 1：学习率（Learning Rate, lr）

在第 9 章我们讲过：Loss 是当前位置的地形高度，梯度是下山最陡的方向，而学习率决定了每一步往前迈多大。

  • 若设太大（如 2e-2 或 5e-3）：步子迈得太大，直接跨过了山谷底部，甚至一脚踩空飞出悬崖。在训练日志中会表现为：Loss 瞬间飙到 10 以上，随后直接报 NaN（Not a Number 溢出爆炸），这在行业里就叫「炸炉（Divergence）」。
  • 若设太小（如 1e-6）：步子迈得像蚂蚁爬，训练跑了 500 步 Loss 几乎纹丝不动（平线形态）。
  • 经验参考：对于 LoRA 这种参数量只占 1%~2% 的轻量适配器，最佳学习率通常在 1e-4 到 3e-4 之间（我们一直在用的 2e-4 是极其稳健的甜点位）。

旋钮 2：有效批次大小（Effective Batch Size）与梯度累加

你在写 TypeScript 时肯定明白：从数组里抽样 1 个元素算出的平均值极不稳定；抽样 32 个元素算出的平均值才具有代表性。训练也是同理：Batch 越大，梯度越准。

但第 9 章的显存数学严酷地限制了我们：在 T4 显卡（16GB）上，单卡物理批次（per_device_train_batch_size）设到 8 差不多就接近显存红线了。如果我想用 32 甚至 64 的大批次来稳定训练，显存装不下怎么办？

ELI5 · 什么是梯度累加（Gradient Accumulation）？

想象你要把 32 箱苹果搬上货车，但你的小推车（显存）一次只能装 8 箱：

  • 物理装载：你推车运 8 箱，先不关货车门（不更新参数）；
  • 往返累加：连续运 4 趟（8 × 4 = 32 箱），把 4 趟运来的苹果总数加在一起；
  • 统一下发：第 4 趟运完后，货车门关闭发车（执行一次优化器 optimizer.step() 更新参数）！

这就是梯度累加：在不增加任何显存负担的前提下，纯靠多跑几个微循环，等效模拟出了超大批次的数学稳定性！

数学等式：

有效批次大小 (Effective Batch Size) = per_device_batch_size × gradient_accumulation_steps × GPU卡数

旋钮 3：学习率调度器（Scheduler：Warmup + Cosine）

为什么不能用固定的 2e-4 从头跑到尾？

  1. 冷启动阶段（Warmup 热身）：训练刚开始时，LoRA 适配器内部全都是随机初始化的数字（矩阵 A 是高斯随机分布，B 是零矩阵）。如果一开始就给最大油门（最大 lr），猛烈的梯度冲击会瞬间把预训练模型原有的良好语义破坏掉。因此前 5%~10% 的步数必须从零慢速爬坡。
  2. 后半程收敛（Cosine 余弦退火）：当训练接近尾声，模型已经无限逼近最优解的谷底。此时如果步子依然很大，就会在谷底左右疯狂晃荡、无法稳定沉降。此时学习率像余弦曲线一样平滑减速，有助于模型在谷底做极其细腻的微调。

▶ 例 8-2 · 开启 Warmup 与 Cosine 调度器配置

training_args = TrainingArguments(
    output_dir = "outputs_tuned",
    per_device_train_batch_size = 4,     # 物理小批次（省显存）
    gradient_accumulation_steps = 4,     # 累加 4 次 ➔ 有效批次 = 4 × 4 = 16！
    learning_rate = 2e-4,
    warmup_ratio = 0.1,                  # 前 10% 的步数慢速热身爬坡
    lr_scheduler_type = "cosine",        # 随后走余弦曲线平滑衰减
    num_train_epochs = 3,
    logging_steps = 10,
    report_to = "none"
)

8.3 评估维度跃迁：跨越 Loss 盲区

在第 9 章中，我们靠 Validation Loss 成功抓到了过拟合。但随着你走进真实工业场景，你必须明白一个事实：

Validation Loss 最低，绝对不代表模型在业务上最聪明！

Loss 的局限性是什么？

Loss 本质上只是在考核：模型预测出的每一个 Token，跟人工标注的数据集里的字眼有多接近。这会导致两种典型误判：

  1. 同义不同词被误罚：标准答案是“开心”，模型回答了“十分愉悦”。在业务上两者意思完全一样甚至更文雅，但因为字面 Token 不匹配，Loss 算出来反而会偏高！
  2. 安全废话套路刷低分：模型如果学会了无论问什么都先背诵一句长达 50 字的标准礼貌用语（比如“您好！非常高兴为您解答这个问题，请允许我为您梳理如下内容…”），它的 Loss 会非常好看，但在用户眼里这完全是低智废话。

现代工业界的解法：LLM-as-a-Judge（大模型裁判）

既然传统的数学指标（Loss、BLEU、ROUGE）无法理解复杂的语义逻辑，目前的工业前沿统一转向了**「以大评小（LLM-as-a-Judge）」**：

这套机制通过让更聪明的超级模型充当裁判，甚至采用双盲赛马（A/B Elo 评分），彻底解决了人工盲目抽检看不过来的瓶颈。

练习 8-A · 极端学习率炸炉实证（亲历发散与震荡）

目标：只有亲眼见过炸炉，才真正理解为什么学习率被称为第一杀手。一键复制下方代码，见证把 learning_rate 放大 25 倍（5e-3）时的灾难现场。

import os, gc, torch
from datasets import load_dataset
from unsloth import FastLanguageModel, train_on_responses_only
from trl import SFTTrainer
from transformers import TrainingArguments

# ① 加载底座与 LoRA
model, tokenizer = FastLanguageModel.from_pretrained(
    model_name = "unsloth/Qwen3-0.6B-unsloth-bnb-4bit",
    max_seq_length = 2048,
    load_in_4bit = True,
)
model = FastLanguageModel.get_peft_model(
    model,
    r = 16,
    target_modules = ["q_proj", "k_proj", "v_proj", "o_proj", "gate_proj", "up_proj", "down_proj"],
    lora_alpha = 16,
    lora_dropout = 0,
    bias = "none",
    use_gradient_checkpointing = "unsloth",
)

# ② 准备 300 条短数据并按 8:2 切分
prompt_style = """### 指令：\n{}\n\n### 输入：\n{}\n\n### 回答：\n{}"""
EOS = tokenizer.eos_token

raw = load_dataset("shibing624/alpaca-zh", split="train")
clean = raw.filter(lambda r: 15 < len(r["output"]) < 100 and "{" not in r["output"])
small = clean.shuffle(seed=42).select(range(300))
formatted = small.map(lambda r: {"text": prompt_style.format(r["instruction"], r["input"], r["output"]) + EOS})

split_ds = formatted.train_test_split(test_size=0.2, seed=42)
train_ds = split_ds["train"]
eval_ds  = split_ds["test"]

# ③ ★ 危险操作：把学习率放大 25 倍设为 5e-3！
args = TrainingArguments(
    output_dir = "outputs_exploded",
    per_device_train_batch_size = 8,
    per_device_eval_batch_size  = 8,
    num_train_epochs = 2,
    learning_rate = 5e-3,        # 正常是 2e-4，这里狂飙到 5e-3
    logging_steps = 10,
    eval_strategy = "steps",
    eval_steps = 20,
    save_strategy = "no",
    report_to = "none",
)

trainer = SFTTrainer(
    model = model,
    tokenizer = tokenizer,
    train_dataset = train_ds,
    eval_dataset = eval_ds,
    dataset_text_field = "text",
    max_seq_length = 2048,
    args = args,
)
trainer = train_on_responses_only(
    trainer,
    instruction_part = "### 指令：\n",
    response_part = "### 回答：\n",
)

trainer.model.config.use_cache = False
print("启动极限学习率 (5e-3) 实验...")
trainer.train()

Early Stopping 早停机制
监控验证集指标，当连续若干步（patience）无突破时自动中断训练以防止过拟合的守卫技术
Gradient Accumulation 梯度累加
在反向传播时不立即更新权重，而是将多个微批次的梯度相加后再统一更新，以时间换取大 Batch 稳定性的显存优化方案
Warmup 热身
在训练初期将学习率从 0 线性增加到目标值的策略，防止冷启动时随机初始化的梯度猛烈冲撞破坏底座先验知识
Cosine Decay 余弦退火
学习率随着训练推进按余弦波平滑下降的衰减策略，帮助模型在后期精准逼近损失曲面的极小值点
LLM-as-a-Judge 大模型裁判
利用更高级别的大模型（如 GPT-4 / Qwen-Max）对微调模型生成的回答进行多维度自动化打分或双盲 A/B 裁决的现代评测标准
